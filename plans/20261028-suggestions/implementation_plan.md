# MMDSKIN 新建议：需求初稿与修改准备

日期：2026-10-29　版本：v0.3　状态：音频优先改动及第二批 R4/R5 已实现并通过程序验证；跨模型碰撞尚未实现。

第二批实现、使用方式和验证结果见 [phase2-verification.md](phase2-verification.md)。下文保留原始方案与验收条件，用于区分程序验证和仍需进行的游戏内验收。

依据：用户附件《MMDSKIN新建议20261028.docx》。代码核对基线为当前 `work` 分支、提交 `2bcb2ee1342555eb523209ed4993f60ff1b304f2`；工程配置为 Minecraft 1.21.1、模组 1.10alpha-1.21.1。下文的实现基础以该提交为基线；实际完成项及程序测试、构建证据见同目录 verification.md。源码核对和程序测试均不代表游戏内验收。

## 新增第一优先级：R0 舞台音频爆音、32 位播放与处理进度

用户补充：异常仅在舞台模式出现，源文件为 44.1 kHz、双声道 IEEE float32 WAV；要求默认采用 32 位，低位深向上转换，并显示加载/处理进度。以此覆盖初稿中的音频实现口径。

已用旧 Java Sound 转换路径复现：输入 +1.05 转成 PCM16 后为 -31131，输入 -1.05 转成 +31130，峰值发生符号翻转。截图只能提示这一可能性；原始音频文件尚未提供，不将样例复现等同于原文件已经验收。

实施：WAV 直接解码为原生字节序 float32，保留合法超出 ±1 的浮点峰值；8/16/24/32 位整数上转浮点，不再默认量化到 16 位。OGG 使用浮点解码；MP3 解码结果上转浮点。上传使用 OpenAL float32 格式，设备不支持时明确报告，不静默降到 16 位。

读取和处理移入后台，显示真实字节/样本进度；主持端预加载完成后再通知开播，观演端加载完成后接入当前帧；取消、重载、失败均清理任务和音频资源。同步修复避免 0.15 秒偏差就直接切断波形，较大跳转先淡出再定位和淡入。

验证按 float32 峰值保真、整数位深上转、声道/字节序、非法样本、同步淡入淡出、加载取消和实际 OpenAL float32 上传分别执行。原计划各项保持分批，不把 R0 的完成当作整个计划完成。

## 一、起草口径与版本安排

本轮建议分为两批。第一批处理手持 PMX 物理与本体碰撞选项、VPD 姿势加载与恢复、舞台结束帧规则核实及可选设置；第一批完成后先交付一个版本。第二批处理手持 PMX 的本体骨骼绑定与独立 VMD，分别评估、分别实现，出现副作用时可单独回退。

保留附件原有的条件：第 3 项先验证“取镜头、动作、音乐三者最短值”的推测，若属实再增加选择结束依据的设置。当前源码与该推测不符，因此本文列出设置方案供后续修改使用，用户随后授权按计划直接修改，本轮已采用该设置方案；默认仍保留旧规则。

以下默认值、异常处理和技术路线均为起草建议；附件已经明确的五项诉求与分批顺序保持不变。未取得实际样例验证前，不承诺完成时间。

| 编号 | 附件诉求 | 当前核对结论 | 修改准备与难度初判 |
| --- | --- | --- | --- |
| R1 | 手持 PMX 开启物理，可选择是否与本体计算碰撞 | 道具已独立加载；现有非世界渲染路径跟随全局物理开关，并非明确禁用物理；每模型有独立 Bullet 世界 | 先验证现有道具物理；跨模型碰撞为高难度项 |

## 二、第一批需求初稿

### R1　手持 PMX 的物理与本体碰撞

允许作为手持替换物的 PMX 使用自身刚体和关节进行物理演算，并提供“与本体碰撞”选项。关闭该选项时，道具仍可进行自身物理演算；开启时，仅使该道具与所属角色本体产生所定义的碰撞，不自动扩展到其他玩家。

**已核实的实现基础**

- `HeldItemPmxRenderer.renderMainHand` 将道具作为独立模型获取，以 `RenderScene.ITEM`、空实体参数渲染，并在 Java 渲染矩阵中附加主手变换。
- `BaseModelInstance.nonWorldDecision` 根据全局物理设置决定是否启用物理，随后进行模型更新。因此先排查“物理没有可见效果”的原因，避免只重复开启已有开关。
- Rust `RuntimeModel` 创建自己的 `MMDPhysics`；当前默认后端 `upstream1201` 中，每个 `MMDPhysics` 创建独立 `BulletWorld`。两个模型都开启物理，不会自然获得跨模型碰撞。

**拟修改方案**

1. 用含动态刚体和关节的道具复现，检查模型加载、物理初始化、更新次数、全局开关和父骨骼运动。道具模型的刚体/关节必须有效；无刚体模型不作为物理失败证据。
2. 将道具的绑定变换、偏移、旋转与缩放整理为统一变换来源，供渲染和物理转换使用。确认快速转手、转身时的重力方向、惯性与坐标转换；只在绘制时乘手部矩阵不足以证明这些行为正确。
3. 为本体碰撞配置增加持久化、复制和校验，建议默认关闭，以保留现有独立演算行为。界面明确区分“道具自身物理”和“与本体碰撞”；是否另设道具独立物理开关属于扩展建议，全局关闭物理仍应生效。
4. 优先做最小碰撞原型，再确定实现路线。完整双向作用需要共享求解上下文或等价的跨模型耦合，涉及刚体归属、坐标空间、碰撞组、步进和释放顺序。
5. 可评估在道具世界加入随本体更新的碰撞代理作为近似方案，但它通常只有单向影响，且未必覆盖本体动态衣物。必须标明差异，不能把它当作完整双向碰撞验收通过。

**验收条件**

- 全局物理开启时，有效道具出现可验证的动态响应；关闭全局物理后不再演算，角色原有物理正常。
- 本体碰撞关闭时两者不相互碰撞；开启时符合约定的碰撞方向和对象范围，并尊重 PMX 碰撞组/掩码。
- 旋转、移动、快速停下、缩放、换模型、切换道具和重置物理后，无明显漂移、爆炸或残留碰撞体。
- 同一画面帧中主渲染、阴影和多次绘制不会造成重复物理步进；跨玩家模型不串扰，资源随模型释放。

**难度与交付边界**

高难度部分是跨模型碰撞，不能按一个设置开关估算。第一批仍以附件前三项为目标；若完整耦合代价过高，应先交付原型结论、影响范围及近似方案，再由用户决定近似或舍弃。仅“道具物理已开启”不等于 R1 全部完成，也不能据此直接宣告第一批完成。

### R2　VPD 姿势加载与恢复

为角色提供清晰可发现的“加载 VPD 姿势”和“恢复默认姿势”操作。VPD 可包含骨骼姿势和表情权重，加载后应给出成功、未匹配或失败反馈。

**已核实的实现基础**

- `VpdFile` 已解析骨骼位移、旋转和 Morph；JNI `ApplyVpdMorph` 会应用二者，并在后续动画求值后保留骨骼覆盖。
- `ExpressionApplicationService` 的 FILE 分支已调用该 JNI；`MorphWheelScreen` 已有表情文件和重置操作，不应重新建立重复的 VPD 引擎。
- JNI `ResetAllMorphs` 已同时清空 Morph 权重和 VPD 骨骼覆盖。它会影响表情，不能直接假设等同于“只恢复姿势”。
- 当前 VPD 加载使用文本逐行读取；日文 Shift-JIS、UTF-8/BOM 和不同换行符仍需用样例验证，不能凭已有解析器就宣称全面兼容。

**拟修改方案**

1. 优先复用现有 VPD 扫描和应用链路，调整入口文案或增加明确的姿势入口，使用户无需从“表情”推断支持全身姿势。
2. “恢复默认姿势”建议定义为清除 VPD 的骨骼覆盖，让角色回到当前正常动作求值结果；它不强制回到静态 T/A 姿势。若要同时清除表情，沿用并明确现有“全部重置”操作。
3. 使用已有 `ClearBoneOverrides` 前先核对覆盖归属：当前外部骨骼覆盖与 VPD 共用相关容器，不能误清其他接口持续写入的姿势。若冲突，需区分来源或明确覆盖规则。
4. 明确 VPD 与行走、舞台、VR/外部姿势输入的优先级。建议切入舞台前处理遗留姿势覆盖，避免其持续盖住 VMD；具体清除/暂停/恢复策略在实现时集中管理。
5. 解析或路径失败时不残留半套新姿势。根据 JNI 返回的骨骼/Morph 匹配数显示结果；零匹配时提示，而非无反馈地当作有效姿势。

**验收条件**

- 纯骨骼 VPD、纯 Morph VPD、混合 VPD 均有明确反馈；不同名称或缺失骨骼可部分匹配，完全不匹配时有提示。
- 连续切换姿势不会遗留上一姿势独有的骨骼覆盖或未说明的 Morph 权重。
- 恢复后可继续待机和行走；如采用仅清骨骼方案，独立表情保持，全部重置仍可用。
- 损坏文件、编码样例、切换模型和舞台进出均不崩溃、不留下错误覆盖；CPU/GPU 路径效果一致。

### R3　舞台结束帧核实与可选策略

**核实结论**

当前 `StageCameraPlaybackSession.resolveMaxFrame` 优先读取解析出的镜头动画句柄的最大帧，没有可用镜头时读取动作动画最大帧。`MMDCameraController` 在配置会话后才加载音频，播放推进完成时触发退出；当前核对路径没有将音乐时长纳入三者取最短值的计算。

还需注意，“镜头动画句柄的最大帧”未必是镜头轨道末帧：`GetAnimMaxFrame → VmdAnimation.max_frame → Motion.duration` 返回该句柄内骨骼、Morph、镜头轨道的最大值。如果一个 VMD 同时含动作和镜头，用这个接口无法准确区分两种末帧。

因此，附件关于“三者最短值”的推测在当前代码基线下不成立。后续仍可增加选择设置，本轮已按用户授权采用设置方案，仍需区分新增策略和旧规则。

**可供修改的策略草案**

| 选项 | 结束依据 | 草案处理 |
| --- | --- | --- |
| 沿用当前规则 | 镜头动画句柄优先，否则动作句柄 | 建议作为旧配置的默认值，保留兼容 |
| 镜头末帧 | 实际镜头轨道最后关键帧 | 需独立轨道时长查询，避免混合 VMD 混淆 |
| 动作末帧 | 实际角色骨骼/Morph 轨道末帧 | 明确多个角色/动作的聚合规则；IK 末帧是否计入需写入契约 |
| 音乐结束 | 成功加载后的音频时长 × 30 | 按现有 VMD 时间基准换算，明确小数帧与最后一帧是否播放 |
| 可用来源最短值（可选） | 有效来源中的最小末帧 | 非附件已确认需求，可作为额外选项评估 |

建议提取独立的结束帧解析器，输入来源可用性、各末帧和策略，输出选定末帧及实际使用的依据。不存在、加载失败或无效数值的来源不能默认算作 0 参与最短值；只有第 0 帧的有效轨道应与“来源不存在”区分。

选择的来源缺失时，建议显示回退提示并沿用当前规则；所有来源都不足以形成可播放时长时，在开始前提示。音乐策略必须等音频加载成功后确定结束帧。播放中临时修改设置建议下次播放生效。

联机时结束帧应由主持端统一确定并传递，不能因观看者的本地偏好或音频加载失败而各自提前结束。需要核对协议兼容和参与者退出行为，不能只改本地相机类。

**验收条件**

- 使用镜头 300 帧、动作 600 帧、音乐 30 秒的分离样例：现有规则应为 300，按动作应为 600，按音乐应为 900；这可区分各策略，但不足以单独证明现有规则不是最短值。
- 再用镜头 900、动作 600、音乐 10 秒的样例：现有规则应为 900，最短值才是 300。比较实际退出时刻并记录。
- 混合 VMD、无镜头、无音乐、音频失败、只有第 0 帧、越界帧及最后一帧显示均有确定行为。
- 观看端与主持端一致，正常结束与手动退出均释放音频、镜头和动作资源。

## 三、第二批需求初稿

### R4　手持 PMX 自定义本体绑定骨骼

允许用户指定道具绑定的本体骨骼，例如右手、左手、头或其他现有骨骼。此处按附件括号内的说明理解“外亲骨”，即运行时选择本体的绑定点；不直接改写 PMX 文件中的骨骼关系。

当前固定调用 `ItemRenderHelper.applyMmdHandMatrix`。可复用 `GetBoneNames` 获取候选骨骼，但 `NativeMatrixPort` 目前只提供手部矩阵读取，需要补充读取指定骨骼当前全局变换的 Java/JNI/Rust 链路。必须使用实际求值后的骨骼变换，不能误用蒙皮偏移矩阵。

拟在模型配置中保存骨骼标识，运行时在当前模型中解析和缓存索引；模型切换后重新解析。旧配置和无效骨骼回退主手并提示。沿用既有局部偏移、旋转、缩放，按“本体变换 → 绑定骨骼 → 道具局部变换”组合，并与 R1 的碰撞空间共用同一变换定义。

绑定位置与“是否显示”分开处理：第一版建议沿用主手非空时替换的触发条件。即便绑定头部，也不自动变为常驻配饰；如果需要空手常驻，应另列扩展，避免改变已有行为。

验收覆盖不同骨骼、骨骼缺失、同名骨骼处理、模型切换、偏移/旋转/缩放，以及骨骼受物理驱动的情况。出现副作用时可关闭自选绑定并回到原主手矩阵。

### R5　舞台内手持 PMX 独立 VMD

允许在舞台资源分配中，为当前道具 PMX 单独选择 VMD；角色本体与道具使用不同的动画句柄和动画层，均由同一舞台帧驱动。道具动作可以包含自身骨骼和 Morph，不能反过来覆盖本体动作。

当前 `ModelRequestKey.heldItem` 已提供独立道具模型身份，可在此基础上增加道具动作分配与生命周期管理。拟修改入口包括 `StageAssignPanel`、舞台播放计划/请求、播放运行时、`StageAnimSyncHelper` 和 JNI 动画端口。道具资源迟到时应定位到当前舞台帧，不从 0 重新开始；每帧不得重复加载 VMD。

拟定行为：未选 VMD 时保留现有静态道具行为；VMD 比舞台短时保持末帧，默认不循环；比舞台长时随舞台结束。道具动作默认不参与 R3 的结束帧计算。停止、重新播放、观看退出、切模型和切道具时，清理或恢复动画状态及物理状态。

道具自身根骨骼动画在绑定坐标内求值，并与 R4 的外部绑定变换组合；不能将世界位移动作和本体变换重复叠加。角色无有效道具时，保持原有物品回退路径。

验收覆盖独立动画、同帧同步、重播、资源加载延迟、VMD 失败、长短不等的动作、多人不同道具，以及停止后的资源释放。完整多人可见需要资源标识和分配信息同步，不能把“本地可见”当作完整联机支持。

若联机同步或底层生命周期改造代价过高，可评估先做本地舞台版本，但需先说明差异；不能默认为附件已经接受的缩减范围。
