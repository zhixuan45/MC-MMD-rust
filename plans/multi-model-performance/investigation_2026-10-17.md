## 已确认的主要负担

### 透明兼容路径仍有大量真实 draw

四杏辞透明窗口 01:44:34.238—01:49:14 附近，逐模型、按 samples 加权统计如下。透明日志与帧日志分别刷新，不能按同行号硬拼逐帧数据。

| 模型句柄 | 透明实际 draw/模型调用 | SUBMIT 均值/调用 | READBACK 均值/调用 | 回读字节/调用 |
| --- | --- | --- | --- | --- |
| 38 | 6513.84 | 6.179 ms | 1.280 ms | 482172 |
| 41 | 6402.74 | 6.193 ms | 0.274 ms | 482172 |
| 43 | 6377.78 | 5.993 ms | 0.260 ms | 482172 |
| 1 | 6762.82 | 6.566 ms | 0.260 ms | 482172 |

这意味着四个均被绘制时，典型负担约为每帧 2.61 万次透明 draw；四模型的 SUBMIT 均值合计约 24.93 ms，回读约 2.07 ms。SUBMIT 包含主体材质 pass 的提交工作，不能全部命名为纯透明 draw 指令耗时。回读计时也包括 barrier 等等待，不代表纯 GPU 等待时间。

所有四模型窗口中，`BATCH_SUBMISSIONS=0`、`GPU_PREPARE=0`，每次调用 `BATCH_FALLBACK=1`、`READBACK_CALLS=1`；`CANDIDATE_REUSE=1`、`CANDIDATE_BUILD=0`。所以候选缓存确实生效，但没有消除逐帧回读和逐 run 绘制。每模型 SORT 约 0.277—0.313 ms，索引重建约 0.718—0.744 ms，上传约 0.015 ms，排序已不是最大的已测阶段。

代码依据：`render/shader/TranslucentBatchShader.java:35` 只返回已注册的本模组原生 Toon 程序；`render/material/TranslucentBatchSubmission.java:24` 在当前程序无相应接口时回退；`render/material/SubMeshDrawHelper.java:132` 在回退后逐 run 调用 `glDrawElements`，实际 draw 计数在第 139 行累计。路径前缀均为 `common/src/main/java/com/shiroha/mmdskin/`。外部光影不能直接套用现有材质表 shader 的合批，这与 BSL 下实测未命中一致；本日志没有逐次打印回退理由，不能排除其他能力条件也参与回退。

### 物理串行求值，低帧率补步放大每帧工作

四模型稳定段的 SHADOW 共求值 17420 次，WORLD 共复用 17420 次且求值 0 次。物理实际执行 68742 个子步、17401 次 step 调用，平均每次 step 为 3.950 个子步，整帧四实例合计 15.785 个子步。单模型所选窗口平均每次 step 为 0.935 个子步，两实例混合窗口为 1.765 个。

`render/backend/BaseModelInstance.java:343` 根据上次更新时间计算 delta；`rust_engine/src/physics/mmd_physics.rs:565` 使用 `1 / fps` 固定步，调用 Bullet step；`rust_engine/bullet_wrapper/bw_api.cpp:336` 记录实际与请求子步数。因此日志已经确认低帧率时每实例每渲染帧补算更多物理步。四模型物理约 25.7 ms/帧，包含同步、求解及回写，不能全部归到单个 Bullet 求解器函数。更细的碰撞、约束成本仍未拆开。

这是一种每帧负担放大机制，不能把“每渲染帧四次物理子步”误写成“同一模型被阴影重复更新四次”。当前 WORLD 缓存正在生效；SHADOW 只是这一帧首次求值所在的位置。原生更新约 26.6 ms 已经包含物理约 25.7 ms，统计时不能重复相加。

### 之前的并行没有覆盖本次场景

`latest.log` 全部 186 条性能记录的 `native.parallelBatches` 都是 0，四杏辞段同样如此。

`player/render/PlayerWorldEvaluationPrepass.java:50` 只遍历 `mc.level.players()`，第 51 行还排除本地玩家；第 67 行要求至少两个合格远端玩家。开头的 `loadedWorldModelCount >= 2` 仅是扫描门槛，没有把绵羊、猪等替换实例加入任务队列。当前绵羊映射、刷羊蛋警告和新模型加载时序，均支持这次为本地玩家配合生物替换进行测试；日志未打印每个模型句柄的实体 UUID，不能据此精确证明每个句柄的实体身份。无论具体句柄身份如何，已测并行计数为零，生物替换不在当前并行覆盖范围内。

另有一个代码层面的问题需要后续复现验证：预处理只在非阴影 WORLD 入口触发，而这次真实首次求值发生在 SHADOW。即使换成合格远端玩家，若阴影已先完成本帧求值，`BaseModelInstance.java:385` 也会因缓存命中返回空任务。不能只把遍历列表从玩家改成所有实体，就认为带 BSL 的并行问题已经解决。

## 已检查但不能认定为主因的项目

四模型描边 CPU 只有 0.185—0.261 ms/帧，约 0.211 ms；描边确实有离屏覆盖、深度拷贝和合成，但本日志没有独立的描边 GPU 阶段计时，仍不能排除 GPU 侧成本。不能仅凭其 2 倍分辨率实现就把它判为主要原因。

四模型 `native.cpuSkinning.SHADOW=0`，透明记录明确 `GPU_COMPUTE`，没有 CPU 蒙皮回退的证据。纸娃娃关闭且相应日志计时为零；稳定段没有 WARN/ERROR 或开始后台加载事件。加载时的 `lightMap.png` 缺失不能解释随后数分钟的稳定逐帧负担。

VSync 和 GPU 性能日志当前开启，可能影响观测，需要单变量对照，但目前没有证据将 30/15 FPS 归因于 VSync 档位。GPU query 实现先检查结果可用性，未发现为读计时结果主动等待 GPU 的路径；诊断开关自身的开销没有单独实测，不能称为零开销。
