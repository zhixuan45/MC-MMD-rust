# 多模型性能问题交接文档

记录日期：2026-10-17（Asia/Shanghai）

## 1. 当前问题

用户在四个相同 MMD 模型同时显示时，帧率直接下降到约 15 FPS。用户提供的截图来自 Minecraft 1.21.1 NeoForge，使用 Iris 1.8.14-beta.1、BSL_v10.1.8 shader、Sodium 0.8.13，显卡为 NVIDIA GeForce RTX 5070 Ti Laptop GPU，CPU 为 AMD Ryzen 9 7945HX。

截图关键数据：

- FPS：15
- `p50=16ms`
- `p98=16ms`
- `p99.5=15 FPS`
- GPU：约 58%
- Iris/BSL 高画质处于启用状态

这表现为持续性帧率上限，而不是偶发卡顿。GPU 没有接近满载，当前优先怀疑 CPU 渲染线程、JNI/native 求值、每实例物理/CPU 蒙皮、透明排序提交或渲染同步。

## 2. 已完成的相关实现

### 多模型 native 求值

文件：

- `common/src/main/java/com/shiroha/mmdskin/player/render/PlayerWorldEvaluationPrepass.java`
- `common/src/main/java/com/shiroha/mmdskin/render/pipeline/NativeEvaluationBatch.java`
- `common/src/main/java/com/shiroha/mmdskin/render/backend/BaseModelInstance.java`

当前行为：

- 在世界实体绘制前收集部分可并行的远端玩家模型。
- 最多使用 3 个工作线程执行独立模型的 JNI 更新。
- 使用模型句柄去重，避免同一 native 实例重复求值。
- 阴影 pass、VR、舞台动画、外部姿态和部分特殊路径继续走同步逻辑。
- Iris 主世界实体路径不再整体禁用，但阴影仍然跳过。

重要限制：

- 预求值队列目前实际只收集玩家模型。
- 舞台模型、生物替换模型、女仆扩展模型可以影响模型数量门槛，但尚未进入同一并行队列。
- 本地玩家模型也不在该远端玩家批处理队列中。
- 并行只覆盖 native 求值，不覆盖主体绘制、材质、透明排序、submesh 读取和 GPU 上传。

### 模型数量快速路径

文件：

- `common/src/main/java/com/shiroha/mmdskin/model/port/ModelDiagnosticsPort.java`
- `common/src/main/java/com/shiroha/mmdskin/model/runtime/ModelRepository.java`
- `common/src/main/java/com/shiroha/mmdskin/player/render/PlayerWorldEvaluationPrepass.java`

当前增加了 `loadedWorldModelCount()`：

- 统计模型仓储中当前 active 的模型实例。
- 排除纸娃娃模型。
- 统计普通玩家、`MOB`、`SCENE`、`STAGE` 和扩展模型。
- 达到两个实例后立即停止统计。

它只用于决定是否进入玩家预处理扫描，不能代表本帧实际可见的模型数量，也没有把所有实体类型加入并行工作队列。

### 透明渲染相关

相关文件：

- `common/src/main/java/com/shiroha/mmdskin/render/material/DrawMaterialCache.java`
- `common/src/main/java/com/shiroha/mmdskin/render/material/SubMeshDrawHelper.java`
- `common/src/main/java/com/shiroha/mmdskin/render/material/TranslucentDrawOrder.java`
- `common/src/main/java/com/shiroha/mmdskin/render/material/TranslucentBatchSubmission.java`

已加入材质状态、alpha 和纹理 resolver 的单次绘制缓存，并保留 Iris/外部 shader 的兼容回退。

外部 shader 没有 MMD 材质表契约，因此 Iris/BSL 下不能简单假设所有透明材质都能跨材质合批。透明排序和状态提交仍可能是渲染线程串行成本。

### 纸娃娃

纸娃娃已经改为在满足条件时复用世界实例的姿态/蒙皮结果，并支持刷新频率配置。它不是本次四模型 15 FPS 问题的首要嫌疑，但纸娃娃和世界模型不能混入同一模型数量统计。

## 3. 当前最可能的瓶颈

按优先级排序：

1. 每个实例仍然独立执行动画、物理、骨骼和 CPU 蒙皮；相同模型资源共享不等于运行时状态共享。
2. native 并行只覆盖远端玩家，四模型场景中的本地玩家、舞台模型、生物替换模型可能仍然同步执行。
3. 主体绘制仍可能串行执行材质 morph、submesh 数据读取、骨骼/顶点上传和 draw call。
4. Iris + BSL 下透明路径可能回退到 CPU 排序和兼容提交。
5. 当前 `loadedWorldModelCount()` 统计的是已加载模型，不是本帧真正可见模型，可能导致在单模型可见时仍触发玩家扫描。
6. 四个相同模型可能有不同 `ManagedModel`/native handle；当前只共享部分静态资源，不能消除每实例更新成本。

## 4. 已确认的误区

- 不能用 `mc.level.players().size()` 判断 MMD 模型负载。舞台、生物替换、女仆扩展和其他实体都可能增加模型实例。
- 不能把“相同模型文件”当成“只需计算一次”。动画、物理、视角、实体状态和姿态仍然是实例独立的。
- 不能只看 GPU 占用判断渲染瓶颈。15 FPS 且 GPU 约 58% 更符合 CPU 或同步等待。
- 不能把 `loadedWorldModelCount()` 当成实际可见实例计数。它目前只是快速门槛。
- 不能默认 Iris 下透明合批一定生效；外部 shader 的兼容路径仍需要单独测量。

## 5. 下一步排查顺序

先做同一场景下的二分对照，保持视角、分辨率、shader、模型位置和动画状态不变：

1. `mmdskin.parallelEvaluation=false`
2. `mmdskin.translucentBatch=false`
3. `mmdskin.gpuTranslucent=false`
4. 纸娃娃关闭
5. 物理关闭或降低物理模型数量

每组至少记录 30 秒平均 FPS、p50/p95/p99 帧时间和以下采样字段：

- `nativeUpdateWorldFrame`
- `native.batchPrepare`
- `native.batchExecuteJoin`
- `draw.body.WORLD`
- `materialMorphFetch`
- `subMeshFetch`
- `scene.WORLD.instances`
- `scene.WORLD.evaluations`
- `scene.WORLD.evaluationReuses`
- `GPU_PREPARE`
- `PREPARED_REUSE`
- `READBACK_CALLS`

如果关闭 `parallelEvaluation` 几乎没有影响，说明瓶颈不在 native 并行；如果关闭透明合批后反而提升，说明当前透明缓存或兼容提交存在回归；如果关闭 GPU 透明路径后无变化，说明 Iris/BSL 已经走 CPU 兼容路径。

## 6. 推荐的代码方向

下一阶段不应继续扩大玩家扫描，而应建立统一的“本帧实际 MMD 世界实例登记表”：

- 玩家渲染器登记实例。
- 生物替换渲染器登记实例。
- 舞台模型渲染器登记实例。
- 女仆/扩展渲染器登记实例。
- 登记时记录 scene、实体、模型句柄、是否可并行、是否透明、是否处于阴影 pass。
- 在实体绘制前完成输入快照，在统一边界提交可并行 native 工作。
- 只对本帧可见且满足独立输入条件的实例加入批处理。
- 保留每实例同步回退，避免舞台、IK、VR、手持物品和外部姿态被错误并行。

这样可以同时解决两个问题：

- 不再通过玩家列表推断全局 MMD 负载。
- 不再把已加载但不可见的模型误认为本帧需要预处理。

## 7. 验证状态和工作区注意事项

- `git diff --check` 已通过。
- 工作区存在大量前序未提交改动，后续 AI 不得使用 `git reset --hard`、`git checkout --` 或覆盖无关文件。
- Gradle 最终编译尚未完成；当前环境曾被 Gradle wrapper `.zip.lck`、`native-platform.dll` 初始化和离线插件缓存问题阻塞。
- 不要把 `.gradle-local/`、临时缓存或探针生成物加入提交。
- 没有完成真实游戏中的 Mixin 应用和四模型画面验收。
