# 多平台兼容性优化计划

本文只记录后续兼容性工作，不实施性能优化，也不修改当前由其他代理处理的 Java/Rust 热路径。执行时应以独立提交推进，避免与性能分支产生文件冲突。

## 目标与边界

目标平台覆盖 Windows、Linux、macOS，以及 x86_64、aarch64。优先检查本分支已更改的 GitHub Actions、原生库产物选择和 TaCZ 注入兼容逻辑。性能重构、渲染算法和物理计算不在本计划范围内。

## 第一阶段：可重复构建基线

在 `.github/workflows` 中编写 clean-checkout 构建流程，显式固定 JDK、Gradle wrapper、Rust toolchain 与 Bullet3 准备步骤。矩阵至少包含 Windows/Linux，macOS 在原生依赖准备完成后启用；每个平台上传 Gradle 日志、Rust 测试结果和最终 native 制品清单。

Gradle 任务必须在干净缓存和复用缓存两种条件下各验证一次。IDE 与 CI 的 Java toolchain 应保持一致，Windows runner 需要显式检查 TEMP/TMP 可写性。此项可使用个人 skill `gradle-ide-parity` 辅助定位环境差异。

## 第二阶段：原生制品与架构选择

建立目标三元组到资源路径的单一映射表，核对 Windows DLL、Linux SO、macOS dylib 的文件名与打包位置。启动时记录规范化后的 OS、架构和最终选择的制品；未知架构返回明确的 unsupported 错误，不静默加载近似产物。

交叉编译产物应通过最小加载测试验证 ABI，而不只检查文件存在。优先覆盖 `x86_64-pc-windows-msvc`、`x86_64-unknown-linux-gnu`、`aarch64-apple-darwin` 和 `x86_64-apple-darwin`，再按实际用户平台扩展 Linux aarch64。

## 第三阶段：TaCZ 注入兼容

不要只依赖方法名启发式匹配。对目标类、方法描述符和关键调用点进行版本/字节码能力探测，检测通过后才启用对应 Mixin。对于 lambda 名称等不稳定目标，将注入拆成按版本或能力选择的配置；非关键兼容注入允许捕获初始化错误并禁用该功能，核心渲染路径则应快速失败并输出可诊断信息。

推荐顺序是“精确版本规则 -> 字节码能力检测 -> 保守禁用”，而不是广泛搜索后强行注入。回退日志需包含 TaCZ 版本、候选签名、实际签名和被禁用的兼容功能，避免吞掉真正的注入回归。

## 第四阶段：验收矩阵

每个平台执行 Gradle 编译、Rust 单元测试、native 加载测试和最小游戏启动测试。TaCZ 至少覆盖当前支持版本、一个相邻旧版本和一个相邻新版本；检查 Mixin 审计日志中不存在意外的 `require=1` 失败。最终将已验证组合写入支持矩阵，未验证组合明确标记为实验性。

## 并行协作约束

兼容性实现优先改动 workflow、平台探测、制品装载和兼容适配层。若必须接触其他代理正在调整的性能文件，先等待其提交并基于最新版本做窄范围修改；不要顺手重排、格式化或重构热路径代码。
